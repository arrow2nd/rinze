# 性能と資源

## 点数づけのスレッド

rinzed は zenz の点数づけを `--threads` (既定は CPU の数で、8 まで) のスレッドで走らせる。点数づけと表記の生成は、接続によらず専用の 1 本のスレッドが一度に 1 つずつ受け持つ。
Linux では llama.cpp が OpenMP (libgomp) でスレッドを分ける。libgomp の既定では、手の空いたスレッドがほかのスレッドを CPU を回しながら待つので、ほかのプロセスで CPU が詰まっていると待つスレッドが互いの CPU を奪い、点数づけが何十倍も遅くなる。
rinzed は環境変数 `OMP_WAIT_POLICY` が無ければ `PASSIVE` にして自分を実行し直し、待つスレッドを眠らせる。`OMP_WAIT_POLICY` を渡せば、その値を使う。
`stress-ng --cpu 32` で 16 コアを埋めた間に Space を 8 回打つと、既定の待ち方では中央値 8.6 秒で 1 回は 10 秒を超え、`PASSIVE` では中央値 1.0 秒、最大 1.6 秒だった。
代わりに負荷の無いときは 2 割ほど遅くなり、点数づけの中央値は `か` (候補 94 件) で 31 ms から 39 ms に、`こう` (239 件) で 69 ms から 82 ms になった (12 回ずつ)。どれも 16 コアの x86_64、8 スレッド、L の辞書で測った。

## 常駐メモリ

既定の 5 つに imas と emoji を足した 7 つの辞書で、rinzed の RSS は待ち受けを始めた時点で 123 MB、コーパスを 3 周打ったあとで 135 MB になる (削減の前はそれぞれ 211 MB と 245 MB)。2 周目からは増えない。
内訳は次のとおり。`/proc/<pid>/smaps` の領域ごとの値と、段階ごとに読み込みを止めたプログラムでの `mallinfo2` から割り出した。

| もの | 大きさ | 削減の前 |
| --- | --- | --- |
| モデルのファイルの写し (mmap) | 72 MB | 72 MB |
| 実行ファイルと共有ライブラリ | 7 MB | 7 MB |
| 辞書 7 つ | 19 MB | 97 MB |
| KV キャッシュ (`N_CTX` 512) | 18 MB | 36 MB |
| llama.cpp の計算用の領域、出力、作業用の領域 | 約 15 MB | 約 30 MB |
| モデルの語彙など | 5 MB | 5 MB |

- 辞書は見出しと候補の文字列を 1 つのバッファに詰め、見出しの順に並べた表を二分探索で引く。文字列ごとに `String` と `HashMap` で持っていたときと引いた結果は同じで (7 つの辞書の 30 万見出しすべてで確かめた)、引く速さも同じ (1 見出しあたり約 250 ns)、読み込みは 210 ms から 90 ms になった。
- KV キャッシュは `N_CTX` に比例し、確保した時点で全体が埋まる。点数づけは 1 回の decode にプロンプトと 64 トークンしか置かず、生成のビームは接頭辞を共有するので、512 でも左文脈 40 字のまま 85 字の読みまで生成できる (1024 では 145 字まで確かめた)。256 にすると 9 MB 減るが、生成できる読みが 40 字ほどまでになる。
- 候補の最後のトークンのあとの logits は使わないので、最後のトークンは decode しない。1 文字の候補はプロンプトの logits だけで点数がつく。llama.cpp は出力の領域を 1 回の decode で載せた件数まで広げて縮めないので、1 回に載せるトークンを 64 までにして、出力の領域を最初の 1.5 MB に留める。点数づけは `こう` (241 件) で 255 ms から 88 ms に、`かんじ` (24 件) で 50 ms から 40 ms になった (直接 zenz で、11 回の中央値を交互に 5 組)。
- 点数は候補を decode する組み方で 1 nat ほどまで動く。削減の前のコードでも、候補の順を逆にするだけで 920 問 3512 候補のうち 1492 候補の点数が変わり、5 問で順位が入れ替わった。組み方を変えたあとの差 (7 問で順位が入れ替わり、1 問で 1 位が変わった) も同じ程度で、コーパスの全区間の結果は変わらなかった。
- 接続 1 つにつき、rinzed のスレッドが 1 本と、メモリが約 0.02 MB 増える。OpenMP のスレッド (`--threads` より 1 本少ない) は、計算を頼んだスレッドごとに作られて残るので、点数づけを専用のスレッドに集めて 1 組だけにしている。接続ごとのスレッドで点数づけをしていたときは、点数づけを頼んだ接続ごとに 7 本と約 0.2 MB 増え、200 接続がそれぞれ 1 回変換すると 1601 本、172 MB になった。いまは 209 本、129 MB になる (L の辞書、`--threads 8`、左文脈を変えて `かんじ` を変換、3 回とも同じ)。

## fcitx5 で使う資源

入れ子の sway (headless) で GTK4 (zenity) に 4 語を変換して打ち、30 秒置いてから、rinze を入れた fcitx5 と `--disable=rinze` の fcitx5 を 4 回ずつ比べた (`/proc/<pid>/smaps_rollup`、`/proc/<pid>/smaps`、`/proc/<pid>/task/*/schedstat`)。

- アドオンの共有ライブラリは 1.9 MB で、コードは 1.3 MB、その半分ほどは Rust の std。fcitx5 の中で実際に読み込まれるのは約 0.85 MB で、ファイルの写しなので、メモリが足りなければ捨てられる。無名のメモリは 0.1 MB 増える。
- RSS は約 6 MB 増えるが、多くはパネルに日本語を描くためのもの (日本語のフォント 2.2 MB、fontconfig のキャッシュ 1.6 MB、harfbuzz、cairo、freetype) で、日本語を描かない比較の側との差に出る。
- スレッドは、アドオンが rinzed を起動すると、その標準エラー出力を読むスレッドが 1 本増える。待つ間は眠っている。打鍵の無い 30 秒の間、fcitx5 のどのスレッドも一度も起きなかった。
- `lto`、`codegen-units = 1`、`opt-level = "s"` でビルドしても、共有ライブラリの大きさはほとんど変わらなかった (4 KB 増えた)。std はビルド済みのものをそのまま取り込むため。`panic = "abort"` にすると C ABI の境界で panic を止められず fcitx5 ごと落ちるので、使わない。
