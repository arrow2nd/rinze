# 性能とリソース管理の方針

常駐デーモンとして日常の入力を支えるため、rinze は「レイテンシの安定性」「常駐メモリの抑制」「高負荷時でも入力を止めないこと」を重視して設計している。

## 推論スレッドとフォールバック

- **専用スレッドへの集約**: zenz によるスコアリングと表記生成は、すべての接続から 1 本の専用スレッドに集約して直列に実行する。接続ごとのスレッドから並列に推論ライブラリを呼ぶと、スレッドプールが接続数に比例して増殖しメモリを圧迫するため、推論の入口を一本化している。
- **タイムアウトによるフォールバック**: 変換要求側は推論の完了を一定時間まで待ち、間に合わない場合は zenz の結果を待たずに[辞書順と学習履歴で変換を継続](../usage/typing.md#zenz-が遅れたときや使えないとき)する。CPU が他プロセスで埋まっている状況でも、日本語入力そのものが長時間ブロックされないことを優先している。
- **OpenMP の待機方式（Linux）**: Linux の llama.cpp で使われる OpenMP（libgomp）は、既定ではアイドルスレッドがビジーウェイトするため、高負荷時にスレッド同士が CPU を奪い合い極端に遅延する。`rinzed` は `OMP_WAIT_POLICY` が未指定の場合に `PASSIVE` を設定して待機スレッドをスリープさせ、高負荷時の応答悪化を抑えている。

## 常駐メモリの抑制

複数のフロントエンドから共有される常駐プロセスであるため、メモリフットプリントを抑える工夫を行っている。

- **コンパクトな辞書表現**: 複数辞書を統合したあと、見出しや候補ごとに個別のヒープ割り当てを行わず、連続したバッファに詰めて二分探索で引く構造としている。起動時間の短縮とメモリ使用量の大幅な削減を両立している。
- **KV キャッシュと出力バッファのサイジング**: zenz の用途は短い左文脈と読みに対する単語変換に限られるため、コンテキスト長（KV キャッシュ）を必要十分なサイズに抑えている。また、1 回の decode で扱うトークン数を区切り、末尾トークンの不要な logits 計算を省くことで、推論ライブラリの作業領域が肥大化するのを防いでいる。

## Apple Silicon 向けの方針

Apple Silicon（macOS）では、ヘテロジニアス構成と電力・メモリ特性に合わせて以下の方針をとっている。

- **高性能コア数の優先**: 推論スレッド数の既定値には総コア数ではなく高性能コア（P コア）の数を使う。高効率コア（E コア）にスレッドがまたがると遅いコアの完了待ちがボトルネックになりやすいためである。
- **CPU 専用ビルド**: zenz のような小型モデルによる短い単語変換では GPU を使う利点が薄く、Metal バックエンドを有効にすると初期化だけで余分なメモリとスレッドを消費する。そのため macOS ビルドでは Metal バックエンドを無効化し、CPU の NEON 向け最適化（重みのリパック）を活かして動作させる。

## ネイティブフロントエンドの軽量化

fcitx5 アドオンや macOS 入力メソッドは `rinze-client` を静的リンクして利用するが、ホストプロセス（fcitx5 本体など）の安定性とメモリ消費に配慮している。

- **シンボルの隔離**: アドオンの共有ライブラリからは C ABI の公開関数とホストのエントリーポイントのみをエクスポートし、Rust 標準ライブラリ等の内部シンボルがホストと衝突しないようにしている。
- **FFI 境界での安全性**: Rust 側でのパニックが C ABI 境界を越えてホストプロセスごとクラッシュさせないよう、unwind を捕捉してエラーとして返す構成を維持している。
